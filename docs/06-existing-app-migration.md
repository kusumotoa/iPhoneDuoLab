# 既存アプリで実際に踏んだ不具合と確認ポイント

画面数の多い既存の UIKit アプリ（ViewController が 200 前後）を iOS 27.1 SDK でビルドし、iPhone Duo シミュレータで垂直バーが出る姿勢を歩いたときに見つかった不具合と、その探し方をまとめます。

**1 つのアプリ・iOS 27.1 Beta のシミュレータでの経験則**です。HIG や Apple のドキュメントに書かれている内容ではないものは、「実測」「解釈」と分けて書きます。アプリ固有の名前は伏せています。

このアプリは `UINavigationBar` / `UITabBar` とも**不透明**（`isTranslucent = false`）で、Auto Layout と SnapKit が混在し、`UIScreen.main` や `view.bounds` から寸法を計算する古いコードも残っていました。同じ条件のアプリほど当てはまります。

## 症状から原因を引く

| 症状 | 原因 | 節 |
| --- | --- | --- |
| バーは出るのに**本文が真っ白** | 不透明バーで `extendedLayoutIncludesOpaqueBars` が `false` | [1](#1-本文が真っ白になる) |
| 垂直バー側の端に**要素が重なる** | 制約を `view` の端に直付けしている | [3](#3-safe-area-を無視した制約) |
| 外側のスクロールビューは直したのに、中の**カードやボタンが見切れる** | 入れ子のコンテナが端を `view` に貼り直している | [3](#3-safe-area-を無視した制約) |
| 下部固定ボタンが端まで張り出す | ボタンを含むコンテナ自体が `view` 全幅 | [3](#3-safe-area-を無視した制約) |
| コレクションの**一部が見切れて、スクロールもできない** | セル幅や高さを画面幅から計算している | [4](#4-画面幅から計算しているサイズ) |
| 特定のライブラリ製 UI だけ小さい・欠ける | ライブラリ内部が `containerView.bounds` で計算している | [6](#6-サードパーティの-ui-ライブラリ) |
| 一括置換した画面で**クラッシュ** | 別階層の view への制約（共通の祖先なし） | [5](#5-制約を機械的に書き換えるときの落とし穴) |

## 1. 本文が真っ白になる

### 実測

- 垂直バーが出る姿勢で、タブのルート画面や push 先の画面が、ナビゲーションバーとタブバーだけ描かれて**本文が真っ白**になった
- 先に手元で `extendedLayoutIncludesOpaqueBars = true` を入れていた 1 画面だけが、垂直バーでも正常に描画された。同じ構造の他画面は白いまま
- 白い画面に**このフラグを足すだけで解消**した。制約や `safeAreaLayoutGuide` の修正は要らなかった

### 解釈（未検証）

`extendedLayoutIncludesOpaqueBars` は**既定が `false`** です（SDK のヘッダにも `Defaults to NO` とあります）。不透明バーがあるとルートビューが従来どおりバーを避けたフレームになり、垂直バーの非対称な safe area とかみ合わずに描画が崩れる、というのが観測から言える範囲の説明です。

**HIG にも Apple の Duo 向けガイダンスにも、このフラグの記述はありません。** iOS 7 由来の API なので、将来の OS で挙動が変わる可能性があります。`edgesForExtendedLayout` は既定の `.all` のままで、不透明バーの場合だけ別のフラグで止められます。

### 対処

```swift
override func viewDidLoad() {
    super.viewDidLoad()
    extendedLayoutIncludesOpaqueBars = true
}
```

バーが半透明のアプリでは出ない可能性があります。まず `isTranslucent = false` を探してください。

## 2. 共通基底クラスに寄せるときの落とし穴

このフラグを 1 行ずつ書く代わりに、既存の共通基底クラスに入れ、フラグを持たない約 120 画面の親クラスをその基底クラスに変えました。**この方法は撤回しました。**

- 基底クラスが `viewDidLoad` で**ナビゲーションバーを無条件に表示し**、左端のスワイプジェスチャーとステータスバー背景ビューを足していた。自前でナビゲーションバーを隠す 3 画面で**実際にリグレッション**が出た
- 基底クラス固有の機能（スクロール時のバー自動非表示）を使っている画面は、120 画面のうち **0** だった。得るものがなく、副作用だけを受けていた
- 基底クラスの `@objc func scrollViewDidScroll` と、サブクラス側の同名メソッドが衝突した。extension からの override は `dynamic` が要るなど、**親クラスを変えると修正が連鎖する**

**結論**

- すでに基底クラスを継承している画面は、基底クラスに 1 行足せば足ります
- 継承していない画面は、親クラスを変えずに各 `viewDidLoad` へ 1 行足します
- 基底クラスに寄せる前に、その `viewDidLoad` / `viewWillDisappear` が**無条件に何をしているか**を読みます

## 3. safe area を無視した制約

垂直バーは leading / trailing の safe area として表現されます。コンテンツを `view` の端に貼っていると、バーの下に潜り込みます。

### 探し方

`view.leadingAnchor` / `trailingAnchor`、SnapKit の `equalToSuperview()` や `equalTo(view)` を出発点にします。**背景を敷くだけの view は端まで広げてよい**ので、コンテンツか背景かを見て判断します。

### 入れ子の落とし穴

外側のスクロールビューを `safeAreaLayoutGuide` に直しても、**その中のカードが自分の端を `view` に貼り直している**と直りません。幅を確定させるために `make.right.equalTo(view)` と書くパターンで、**同じコードが 3 画面にコピペされていました**。1 画面の報告は、同じパターンの氷山の一角として扱います。

### 下部固定ボタン

ボタンを含むコンテナ全体を `view` 全幅に貼り、内側は固定パディングだけ、という作りがよくあります。コンテナごと `safeAreaLayoutGuide` に貼り直せば見切れは直ります。

ただし、これだと**コンテナの背景が垂直バーの背後まで広がりません**。[99-checklist.md](99-checklist.md) の「背景は safe area の外側やバーの背後まで広げる。操作可能な要素は safe area の内側に置く」に沿うなら、背景だけを広げて操作要素を内側に置くのが本来の形です。

背景を広げる標準部品として、SDK に `UIBackgroundExtensionView`（iOS 26.0+）があります。今回は見た目の仕上げとして**採用していません**。

## 4. 画面幅から計算しているサイズ

### 実測

`UIScreen.main.bounds.width` や `view.bounds.width` でセル幅を求め、コレクションの高さを「幅 × 比率」で固定し、スクロールを無効にしている画面がありました。垂直バー付きの姿勢で、セルの一部が見切れ、**スクロールもできない**状態になりました。

### 解釈

垂直バーの分だけ**コンテナの実幅が画面幅より狭い**のに、セル幅は画面幅から計算されるため、大きすぎるセルが 1 行に入りきらず、行数が増えます。高さは固定でスクロールも無効なので、はみ出た行は見えず、動かすこともできません。

### 対処

- セル幅は画面ではなく**コンテナの実幅**（`collectionView.bounds.width`）から計算する
- 高さを幅から決めるなら、`viewDidLayoutSubviews` で**実幅が変わったときだけ**制約の定数を更新する。毎回制約を張り直さない
- 幅に比例する高さは、aspect ratio 制約に置き換えられないかを先に検討する。`static` に画面幅から計算していたセルの高さを、自己サイズ + aspect ratio 制約にして解決した例がある

## 5. 制約を機械的に書き換えるときの落とし穴

`view.safeAreaLayoutGuide` への一括置換では、**ビルドが通ってもクラッシュ**します。

- 内側の view が `view` の階層にまだ追加されていない状態で、`view.safeAreaLayoutGuide` に対する制約を有効にすると、「共通の祖先がない」ためクラッシュした。**外側の view を先に `addSubview` して制約を張り、そのあとで内側を足す**順序にする
- クラッシュは表示時や、タップして画面遷移したときの実行時に出る。一括修正した画面は**実際に開いて**確かめる

## 6. サードパーティの UI ライブラリ

サイドメニューの [jonkykong/SideMenu](https://github.com/jonkykong/SideMenu) 6.5.0 は、表示パネルのフレームを `containerView.bounds` だけから計算しており、safe area を考慮していません。垂直バー付きの姿勢でパネルが小さくなり、左上に余白が出ました。

2026-09 時点で 6.5.0 が最新タグかつ master の先頭で、**上流に修正はありません**。このアプリでは未対応のまま保留しています。

サイドメニュー、ポップアップ、ページャー、独自タブバーなど、**自前でフレームを計算する UI ライブラリ**は、自分のコードとは別に洗い出します。

## 7. 画面サイズと端末の参照

- 画面の高さで端末を判定する関数（iPhone X 系かどうかなど）は消し、呼び出し側を `view.safeAreaInsets.bottom > 0` の判定に置き換えました
- `UIScreen.main` は、[99-checklist.md](99-checklist.md) のとおり `window?.windowScene?.screen` や `traitCollection.displayScale` へ置き換えるのが本筋です
- このアプリでは、ビューが手元にない `static` な計算が多く、**暫定として keyWindow から bounds を返すヘルパー**を挟みました。`UIApplicationSupportsMultipleScenes = false` の単一シーン構成なので、現状は実害がありません。マルチシーン対応のアプリでは使えない手です

## 8. 進め方

1. iOS 27.1 SDK でビルドし、垂直バーが出る姿勢で、タブのルート・push 先・モーダル・サイドメニューの遷移先・ポップアップ・画像ビューアを**全部**歩く
2. 症状を上の表に当てはめて原因を決め、**同じパターンを grep で全体から探す**。画面ごとの目視報告だけで進めると、同じ原因の取りこぼしが続く
3. 直したら、その画面を実際に開いて確かめる

```sh
# 画面サイズの直接参照
grep -rnE "UIScreen\.main" Sources

# view の端に直接貼っている制約（背景 view は正当なので目視で仕分ける）
grep -rnE "equalTo: *view\.(leading|trailing)Anchor|equalTo\(view\)" Sources

# 画面幅・ウインドウ幅から計算しているサイズ
grep -rnE "(view|window)\.bounds\.width|UIScreen.*width" Sources

# フラグの有無と、不透明バーの有無
grep -rn "extendedLayoutIncludesOpaqueBars" Sources
grep -rnE "isTranslucent *= *false" Sources
```

grep は出発点で、誤検知を含みます。シミュレータの操作と、SourceKit が新 API を認識しない落とし穴は [03-verification.md](03-verification.md) を参照してください。このアプリでは `No such module` 系の誤検知も多数出ましたが、実際にビルドすれば通っていました。

## このアプリで未対応・未検証のもの

- 背景をバーの背後まで広げる対応（`UIBackgroundExtensionView`）
- サイドメニューライブラリの safe area 非対応
- 一括の基底クラス変更から**除外した**ポップアップ系の 8 クラス（垂直バー付きの姿勢での動作を未確認）
